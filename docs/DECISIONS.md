# Framework decisions

Decisions about the framework itself. Each site keeps its own `DECISIONS.md` for its kickoff answers.

| Date | Decision | Why |
|---|---|---|
| 2026-10-22 | The framework lives in its own repo, `framework-b`. Each site gets a new, separate repo. No site's history or content is shared | Keep every site and the framework independent |
| 2026-10-22 | Page layer: Astro 7, mostly static output, structured so EmDash can be switched on without restructuring | Reusable components for agents; fast static pages |
| 2026-10-22 | Forms: the framework's own multi-step form engine, driven by a JSON schema. SurveyJS stays an option for complex branching | About 5 KB compressed vs about 450 KB for SurveyJS core + UI; already passed axe and Lighthouse |
| 2026-10-22 | Every form is an auto opt-in: one line under the submit button says the visitor will get emails and can unsubscribe at any time | Owner's choice. Allowed under US CAN-SPAM. Sites targeting the EU or Canada are flagged, because GDPR and CASL generally require consent |
| 2026-10-22 | Two modes: idea (`workers.dev`) and launch (own domain), with a `promote` script between them | Most launches are cheap demand tests that may never get a domain |
| 2026-10-22 | Idea-mode email goes through a Google Apps Script mailer in the owner's Gmail: a notification to the owner and an optional auto-reply to the lead | Cloudflare can only send from domains set up for Email Routing, and `workers.dev` isn't one. Apps Script is free (100 recipients a day on a personal Gmail) and needs no domain |
| 2026-10-22 | Launch-mode email: Cloudflare `send_email` for owner notifications; Resend Free on `mail.<domain>` for lead confirmations; newsletters from `updates.<domain>` | Separates the domain's web reputation from its email reputation |
| 2026-10-22 | Lead confirmations are plain transactional mail: text plus minimal HTML, one link, no tracking, no `List-Unsubscribe` headers | Bulk-mail headers and styled HTML sent the test build's confirmations to Gmail Promotions |
| 2026-10-22 | R2 uploads are on by default: a "Do you need to send us something?" file field on the contact form | Keeps the upload path tested on every site |
| 2026-10-22 | Search indexing is a per-site choice in both modes; ideas default to `noindex` | Some ideas should be found from day one |
| 2026-10-22 | Client editing (EmDash) is a per-site switch in both modes. Each EmDash site needs its own D1 and R2 | An assistant or co-worker may need to edit content |
| 2026-10-22 | Ideas share one D1 and one uploads bucket; one account-wide backup Worker covers every site | The Free plan allows 10 D1 databases and 5 Cron Triggers per account |
| 2026-10-22 | Nothing a live site needs runs on the owner's machine. CI is Workers Builds; schedules are Cloudflare Cron; state is in GitHub | Owner's standing rule |
| 2026-10-22 | Design direction is asked through a design intake, not silently inferred (autopilot is an explicit exception, below) | Undirected AI builds converge on the same look |
| 2026-10-22 | Sites carry a vendored copy of `packages/core` stamped with a version. Updating means an agent copies a newer tagged version in on a branch, the preview and QA gate run, and the owner merges | A copied template never receives later fixes. Vendoring avoids build-time credentials for the private repo, and nothing reaches a live site without a passing preview |
| 2026-10-22 | Decided by the owner: the Cloudflare change token lives once as a GitHub Actions secret; every Cloudflare-changing step is a workflow agents trigger; agents hold only a read-only token for diagnostics. Amended the same day: the secrets and the callers live in a private ops repo, because `framework-b` became public | One place to rotate; agents never see the change token. Verified 2026-10-22 that a cloud agent session can trigger workflows by push and by `workflow_dispatch`. GitHub Free gives private repos 2,000 Actions minutes a month, and organization secrets don't reach private repos on Free ([GitHub docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions), checked 2026-10-22) |
| 2026-10-22 | Paid design-reference libraries (Refero, Mobbin) are optional inputs, never required | Owner's choice |
| 2026-10-22 | Autopilot design is allowed: when the owner says "autopilot" or doesn't answer, the agent infers answers, builds three tiles, ranks them by pairwise vision comparison, and marks every choice `inferred`. "Redo the design" re-runs the intake later | Owner's choice; recommended mainly for idea sites |
| 2026-10-22 | Pushes to `main` go live immediately through Workers Builds, so `main` takes changes only through pull requests. Enforcement: free pre-push hook (PR #1) unless the owner chooses GitHub Pro, which enforces branch protection on private repos ([GitHub docs](https://docs.github.com/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/about-protected-branches), checked 2026-10-22) | On the first live build an agent made 10 commits straight to `main`, each deployed without a preview |
| 2026-10-22 | The design phase is approved as proposed (nine-step intake). Free tools from the second research round supplement it without new questions; Apify and paid libraries stay optional | Owner's review. Gallery and review scraping are rejected on terms; fonts are OFL-only until Fontshare's licence is read |
| 2026-10-22 | Uploads go through the Worker: the submit response returns a signed single-use URL, and the file is streamed to R2. No presigned R2 URLs | No R2 S3 key pair per site and no bucket CORS. Streaming stays inside the Free plan's 10 ms CPU limit ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), checked 2026-10-22) |
| 2026-10-22 | Indexing headers for static pages come from a generated `_headers` file, not Worker code | Static assets are served without running the Worker; `_headers` supports host patterns such as `https://:worker.:subdomain.workers.dev/*` ([static assets headers](https://developers.cloudflare.com/workers/static-assets/headers/), checked 2026-10-22) |
| 2026-10-22 | One `SIGNING_SECRET` per site signs unsubscribe links and upload URLs, with a distinct prefix for each use | One fewer secret to set and rotate |
| 2026-10-22 | Filling in any form re-subscribes a visitor who unsubscribed earlier | Owner's rule: every form is a sign-up form, so a new submission is a new opt-in. Each lead row records the wording shown |
| 2026-10-22 | The Apps Script mailer runs in the owner's existing Gmail for now; the owner filters it in his mail client and may move it to a dedicated account later | Owner's choice. Moving later means redeploying the script and updating `MAILER_URL` and `MAILER_SECRET` |
| 2026-10-22 | Backups use D1's export API from a scheduled Workflow, covering every database in the account, streamed to R2 with 90-day expiry | No per-site bindings or registry to keep in sync; each step retries on its own and stays inside the Free plan's 10 ms CPU per step. Pattern from Cloudflare's own example ([backup D1](https://developers.cloudflare.com/workflows/examples/backup-d1/), checked 2026-10-22) |
| 2026-10-22 | `framework-b` is public (owner's choice), so it holds no list of real sites, no site names and no account identifiers. Backups and other ops discover resources from the Cloudflare API instead | Public repos get free branch rulesets and unlimited Actions minutes |
| 2026-10-22 | Site repos are created by a workflow in the private ops repo with a fine-grained GitHub token (`GH_SITES_TOKEN`), not by hand | Owner's choice: one prompt per site |
| 2026-10-22 | Self-test sites (`selftest-*`) are torn down without asking each time, including their GitHub repo. Their rows are still exported to `framework-backups` first. Real sites need the owner to type `delete <id>` | Owner's approval. Self-tests run often and hold only test data |
| 2026-10-22 | The Cloudflare Workers and Pages GitHub app has access to all of the owner's repositories | Needed so Workers Builds can connect each new `site-<id>` repo without a manual step. Owner changed it |
| 2026-10-22 | The backup Workflow is started by a Worker Cron Trigger, not by Workflow `schedules` | Deploying with `schedules` failed: "scheduled Workflows require a paid Workers plan". Cron Triggers are on the Free plan (5 per account; this uses 1) |
| 2026-10-23 | Client editing signs editors in through Cloudflare Access (`<id> editor` on `/_emdash/*`), not EmDash passkeys or email links | Same login as `/admin`; email sign-in would need Cloudflare Email Sending to arbitrary recipients, which needs Workers Paid. EmDash supports Access as its auth mode |
| 2026-10-23 | EmDash content uses its own D1 database, media bucket and session KV per site, bound as `CMS_DB`, `MEDIA` and `SESSION`; leads stay in `DB`/`UPLOADS` | EmDash tables can't be shared between sites; core and leads stay unchanged |
| 2026-10-23 | EmDash's maintenance Cron Trigger runs hourly, not every minute | It only needs to run that often for scheduled publishing; one trigger per site whatever the frequency, so the account limit (5) is the real constraint |
| 2026-10-23 | `editing on` is a switch script that rewrites the site from `starter/editing/`, not a runtime flag | Static sites keep no EmDash packages and stay fully static; an editing site is an ordinary EmDash-on-Astro project an agent can read |
| 2026-10-23 | An idea site may be indexed when the owner asks (`indexing: on`). Its workers.dev address becomes canonical and indexable; previews and other hosts stay noindex | Owner's choice for the first real site |
| 2026-10-23 | A newsletter asked for on an idea site starts as subscriber collection only: every form already opts people in, with one-click unsubscribe. Sending starts at launch, from the site's own domain | Bulk email from a free address hurts deliverability and needs a postal address (CAN-SPAM); the newsletter module is launch-only (SPEC section 10) |
| 2026-10-23 | `DESIGN.md` (Google format, linted by `@google/design.md` 0.4.0) is the only source of the look; `tokens.css` is generated, Tailwind's default palette is switched off, and a fixed token contract lets one section library serve every design | Sections can't drift into raw colours, and any design that meets the contract (including contrast) works with every section |
| 2026-10-23 | One section schema serves static sites and EmDash: the same definitions check `src/content/*.json`, render the components and become EmDash block types | An editing site and a static site share components and content shape; switching editing on moves the page content in unchanged |
| 2026-10-23 | Forms outline inputs with a `field` colour that must reach 3:1 against the background; `line` stays decorative | WCAG 2.2 1.4.11 (non-text contrast). The starter used `line` for input borders at about 1.3:1 |
| 2026-10-23 | Autopilot design for the first real site: the owner asked for "trustworthy and friendly" and delegated the rest; the agent chose the direction from research and recorded every inferred business promise in the site's `PRODUCT.md` for the owner to confirm | Owner's instruction |
| 2026-10-23 | Sites are updated by `scripts/site/update.mjs`: a three-way merge of every framework-owned file (starter and core) from the commit in the site's `framework.lock.json` to the new ref, on a branch, tested, then a pull request in the site repo. Conflicts are left for a person as `<file>.framework-new` | Extends the vendored-core decision to the starter files: fixes to scripts, sections and layouts reach existing sites without overwriting site edits, and nothing reaches production without the owner's merge |
| 2026-10-26 | Preview checks get through Access with a service token minted per run (30 minutes, deleted at the end), admitted by one reusable Service Auth policy that accepts any valid service token on each previews application | No long-lived secret to store or rotate; the session can't write ops secrets anyway. Only account administrators can create service tokens, so the policy admits nothing else |
| 2026-10-26 | QA sends Access headers only to the checked origin, including inside Lighthouse | Third-party scripts on the page (Turnstile) must never see the token; Access's strict mode needs the headers on every request |
| 2026-10-26 | Kickoff answers live in the site's `brief.json`, each marked stated, inferred or default, and `create` accepts the brief | One prompt becomes one checked file; DECISIONS rows come from it instead of being hand-written |
| 2026-10-26 | Impeccable's detector is part of the QA gate (source, and each page at 1280 and 390 px through `--cdp`); its DESIGN.md colour, radius and font-size advisories fail the gate; no Stylelint | One tool checks both the AI-design tells and the design contract on the rendered page, including previews behind Access. Stylelint would only see CSS, while the starter styles mostly with Tailwind utilities |
| 2026-10-26 | Style tiles are real builds of the site per draft, not mock-ups; the autopilot judge is the agent's own vision model answering prepared ballots, not an API call | Tiles show exactly the fonts, tokens and components the site would ship. The judge was calibrated as the session model (trials.md); calling another model would need a key and a new calibration |
| 2026-10-26 | Image credits live in `design/credits.json`, seeded into existing sites once by `site update` | `src/content/` holds pages; a ledger the framework ships must not be overwritten once the site edits it |
| 2026-10-27 | Full sites are content files: every `src/content/<slug>.json` is a page, rendered by one route from the section library | One way to build any page; the same content checks, components and QA cover every page |
| 2026-10-27 | Images live in `src/assets/images/` and go through Astro's `<Image>`; open-licensed photos come from Openverse via `scripts/images.mjs` with credits written automatically and a `/credits` page | Optimized responsive images with no service to pay for; licence terms met by construction; the agent looks at a contact sheet before choosing |
| 2026-10-27 | CRM mirror without a Cloudflare Queue: the Worker copies each lead in `waitUntil` to a Google Sheet (through the Apps Script mailer) and/or a signed webhook, keyed by the lead id; the ops `site crm sync` resends safely | The token Workers Builds creates has no Queues permission, so it could not register a queue consumer on deploy; D1 already keeps every lead and both targets dedupe by id |
| 2026-10-27 | Drips run as one Cloudflare Workflow instance per lead, configured in `site.config.json`, sent through Resend from the site's `mail.<domain>` | No Cron Trigger (the Free plan allows 5 per account) and no Queue (the Builds token can't register a consumer); a Workflow deploys with Workers Scripts Write, and sleeping instances don't count toward the 100 running ones. Emails live in the config so the Worker has them without a build step |
| 2026-10-27 | `editing off` exports with EmDash's own `export-seed` from a SQLite copy of the content database, and keeps the static files in `editing/static/` | `export-seed` is EmDash's documented export, so a schema change inside EmDash doesn't break it. The site repo has no other copy of its static files once `on` has replaced them. Nothing in Cloudflare is deleted, because the content database holds the editors' history |
