# Site agent instructions

This site was built with Framework B. `site.config.json` holds every brand value; nothing brand-specific is hard-coded anywhere else.

## Layout
- `site.config.json`: name, mode, host, owner inbox, forms (JSON schema), email mailers, navigation, Turnstile site key.
- `src/pages/`, `src/layouts/`, `src/components/`: the Astro 7 site. `Form.astro` renders any form from its schema.
- `DESIGN.md`: the design contract in Google's DESIGN.md format. `src/styles/tokens.css` is generated from it by `node scripts/design-tokens.mjs`; never edit tokens.css by hand. Use token utilities only (`bg-surface`, `text-ink`, `text-headline`, `rounded-card`, `px-gutter`), never raw colours or sizes: Tailwind's default palette is switched off.
- `src/sections/`: the section library (hero, steps, features, pricing, area, faq, cta, form, text, split (text and image), gallery, list (up to three lists of checks, crosses or numbers), people (the owner's own photos)). Text fields take `**bold**`, `*italic*`, `==accent==` (a word or two in the accent colour; headlines take it too) and `[label](/path)` links; nothing else is rendered as markup. `schema.js` defines every section once; the same definition checks static content, renders the Astro component and becomes an EmDash block type when editing is on.
- `src/content/<page>.json`: a page's sections, in order. `src/pages/index.astro` renders `home.json`; every other `<slug>.json` is the page `/<slug>` (`src/pages/[page].astro`) and needs a `title` (and ideally a `description`). Every page starts with a hero. Add the page to `nav` in `site.config.json`. `"noindex": true` keeps a page (a thanks page) out of search results and the sitemap; `privacy.json`, `not-found.json` and `contact.json` replace the generated privacy, 404 and contact pages with the owner's own; a `title` in `home.json` is the home page's whole `<title>`. Check content with `node scripts/check-content.mjs`.
- Images: files in `src/assets/images/`, used in image fields as `{ "src": "<file>", "alt": "<what it shows>" }` (hero, split, gallery). Astro serves them as resized WebP. Where a layout crops a picture (a wide hero band, a card, a phone screen), add a focal point to keep its subject in view: `"focalX"` and `"focalY"`, shares of the width and height from 0 to 1 (`"focalY": 0.15` keeps a sign near the top in the frame; EmDash stores the same two fields). Owner photos first; otherwise `node scripts/images.mjs search "<query>"` (add `--source loc` for Library of Congress photographs with no known restrictions), look at the contact sheet it makes, then `node scripts/images.mjs add <id or loc:id> --as <name> --alt "..." --for "<slot: why>"` (credit written for you; for an archive scan, look at `design/image-candidates/<name>-crop.png`). A photo taken off a page goes to the library: `node scripts/images.mjs shelve <file>` (`unshelve`, `library`). `/credits` lists credited images and the footer links to it.
- `src/worker.js`: three lines that start the core runtime. Don't add routes here.
- `core/`: a vendored copy of Framework B core (version in `core/VERSION`). Never edit it here; it is replaced by framework updates.
- `framework.lock.json`: the Framework B commit this site was last built or updated from. Don't edit it by hand.

## Framework updates
- Framework-owned files (everything from the starter except brand, content, design contract, records and `wrangler.jsonc`) are updated by the ops repo's "Site update" workflow. It runs Framework B's `scripts/site/update.mjs` on a branch, tests a copy (build, e2e, QA with Turnstile test keys) and opens a pull request here with a report.
- The update does a three-way merge: files the site never changed are replaced, site changes are kept and merged with the framework's, and overlapping changes are left as conflicts with the framework's version in `<file>.framework-new`. Resolve each one, delete the copy, then merge.
- If the report says the EmDash content model changed, the deployed content database keeps its old model until it is migrated; follow EmDash's "Evolving a deployed site" guide before merging.
- `PRODUCT.md`, `DESIGN.md`: the design contract. `STYLE-GUIDE.md`: the style guide everything after the home page is made from (rendered to `design/style-guide/`). `DECISIONS.md`: kickoff answers. `HANDOFF.md`: URLs, monitors, renewals, owner-attested settings. `SECRETS.md`: secret names only.

## Commands
- Build: `npm run build`.
- Local run: `npm run db:migrate:local`, then `npm run dev`. Put test values in `.dev.vars` (copy `.dev.vars.example`).
- End-to-end test: `npm run build && npm run test:e2e`. It uses a local Worker, a real browser and Turnstile test keys, and sends no email.
- QA gate: `npm run build && npm run qa` (local), `npm run qa -- --url <preview-url>` (P6), `npm run qa -- --url https://<domain> --launch` (P8). It fails on any check; screenshots and the report land in `qa-output/`.
- Migrations: `npm run db:migrate:remote` (never `d1 execute` with schema SQL).
- Client editing (EmDash): `node scripts/editing.mjs on` switches it on; `node scripts/editing.mjs off --remote` switches it off and brings the published home page and its images back into files (see "Client editing" below). Local tests of an editing build first need `node scripts/fill-test-placeholders.mjs` if the site has no real resources yet.

## Client editing (EmDash)
- When `site.config.json` has `"editing": { "enabled": true }`, pages that read EmDash content render on request (cached in Workers Cache); every other page is prerendered (`export const prerender = true`).
- Editors use `/_emdash/admin`, behind Cloudflare Access (the `<id> editor` application). To add an editor, add their email to that application's policy. The first person to open the admin runs the setup wizard; choosing the sample content brings in the site's current copy from `seed/seed.json`.
- Content lives in its own D1 database (`CMS_DB`) and media bucket (`MEDIA`), separate from leads (`DB`, `UPLOADS`). Previews use their own copies of both.
- The content model is in `seed/seed.json`. To change a deployed site's model, follow EmDash's "Evolving a deployed site" guide; don't edit the seed and expect it to re-apply.
- The hourly Cron Trigger runs EmDash's scheduled publishing and maintenance. The Free plan allows 5 Cron Triggers per account.
- Switching off: `node scripts/editing.mjs off --remote` (needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`) on a branch, then a pull request. Only the published home page is exported; unpublished drafts are not. It deletes nothing in Cloudflare and lists what the owner can remove. Confirm the source of every image it credits.

## Design
- Four lenses for every design decision, never the industry alone: `design/research.md` records the business and its goals (from `PRODUCT.md`), its field, current design (dated trend reports and galleries from the last 12 months, outside the field too: what fits, what to avoid) and the site's own look (its photos' era and texture, type, colour; if nostalgic, for whom and for what). Write it before drafts or routes; drafts, routes, the logo, the style guide, images, print and social pieces all draw on it. The content check fails a missing lens and notes an unwritten or undated one.
- Compare looks before choosing one: `node scripts/design-tiles.mjs <draft.md> <draft.md> [<draft.md>]` renders each draft on this site's real content into `design/tiles/`. It swaps DESIGN.md and tokens.css while it builds and puts them back at the end; if a run was killed, the next run restores them first. On autopilot, `node scripts/design-judge.mjs prepare`, answer each ballot LEFT or RIGHT, then `tally`.
- Before drafts, with an owner: this-or-that pairs. Write `design/pairs.json`, `node scripts/design-pairs.mjs render`, send the PNGs, record answers with `pick <id> a|b` (`defaults` if the owner is silent).
- After the gates pass: at most three critique rounds with `node scripts/design-critique.mjs start | score | compare | decide` (rules in its header). A fix stays only if it wins the pairwise judge both ways round.
- Every image in `public/` or `src/` needs an entry in `design/credits.json` (source, alt text; creator, licence and link for stock). A generated image is never the business's own people, premises, products or work, and never a recognisable face.
- Say what AI did with every picture: the tools record it as `ai` on each credit (`chose`, `cropped`, `treated`, `alt`, `drew`, `generated`); add `"alt"` yourself when you write an owner photo's description, and name your model once as `"aiBy"` in `design/credits.json` (or pass `--by "<your model>"` to `images.mjs`, `logo.mjs pick` or `generate-image.mjs use`). The Website assets page lists each picture once: where it comes from, where it appears and what the model did; nothing is claimed without a record. For the owner's own pictures, write where they come from in their words as `credit` ("A still from our film, provided by the owner."); the page never says the model chose them.
- Change the look in `DESIGN.md`, then run `node scripts/design-tokens.mjs`. It lints the file with `@google/design.md` and checks the token contract (required colours, type levels, radii and spacing) and the `composition` and `imagery` blocks (allowed values in its header). It also checks the WCAG AA contrast pairs, then writes tokens.css and `src/styles/design.json`. Fonts must be installed Fontsource packages (`npm i @fontsource-variable/<family>`).
- `composition` sets the skeleton for the whole site: alignment, density, separation (tone bands, hairlines or none), card style, image shape, motion (none, subtle, expressive; always off with reduced motion), the phone budget, the logo's size, the footer (`wordmark` or `plain`) and the eyebrow ornament (`none` or `mark`), plus the route's title case (`titleCase`: as-written or upper), hero layouts (`heroes`: the home page's, and a family for every other page) and the section every content page ends on (`closing`). `imagery` sets the picture style, an optional secondary style, a treatment (duotone, tint, warm, cool, mono) and grain.
- Balance: no section leaves one side of a wide screen empty. A reading column keeps the prose width, so a section of text goes beside its headline (`split`, the default for text with a headline), in a centred column (`center`, `stack`), or beside pictures (people `aside`, `split` sections). Forms sit beside their introduction (`split`); a single list goes beside its headline. The QA gate measures each section's weight either side of the middle at 1280 px.
- Crops: a picture a layout crops by a third or more of its width or height names its focal point on that axis (`focalX`, `focalY`), even when the centre is right. Look at `qa-output/crop-sheet-1280.png` and `crop-sheet-360.png` (each crop over its whole picture) and move the focal point until every subject is in its frame; if no crop works, change the layout (a poster card shows a portrait photo whole).
- Long text under a big heading: text `wide` sets the headline across four fifths of the page and the text in two columns beneath it (a single paragraph sits beside the headline instead, so neither half is empty; several paragraphs flow on across the two columns); set one or two key words of the headline as `==accent==` (a word or a short phrase, never a sentence, not every headline). The people section's closing note is set the same way.
- Hero `fade`: the photo fills the band's height on the right and fades into the background towards the headline; the text stays on the plain background.
- Footer: link groups two to a row on phones; with a logo, the footer ends on it across the content width (`composition.footer`: `wordmark` or `plain`). `composition.ornament: mark` puts the logo's mark (the favicon's shape) before every eyebrow label.
- Spot colour (for black and white photos, when the owner wants it): one object per photo in the accent colour, chosen for the photo's story (clothing, a camera, film, a ticket, a sign), never a face or skin. `node scripts/spot-colour.mjs mask <file> --what "..." --point x,y [--not x,y] [--box l,t,r,b]` (or `--tone dark|light --quad ...` for lettering), look at `design/spot/<name>/preview.jpg`, then `apply <file> --by "<your model>"`; `undo`, `sheet`. The whole object, and nothing beside it: build an outline from pieces with `--add` and `--cut` (each with its own points and box), draw what the segmenter misses or over-reaches by hand (a bare `--box` or `--quad`, `--ellipse cx,cy,rx,ry`), outline an owner's photo on its colour original with `--from <file>`, fill small holes with `--fill`; for bulbs, `--tone light --spots <radius>` and then cut the sign's face; `--open <radius>` drops slivers thinner than the letters; `--local <radius>` follows a tube across uneven light, `--specks <pixels>` drops grain without breaking it and `--grow <radius>` widens it to its glow; a tube no method finds is traced in narrow `--quad` bands along its centre line. Pieces build on `design/spot/<name>/outline.png` (hard-edged); `mask.png` is the soft-edged copy the tint goes through. Look at the preview zoomed in after every piece. To crop a photo, `undo` it, `node scripts/images.mjs crop <file> --cut l,t,r,b [--also <colour original>]`, then outline it again. Write the owner's brief in plain words as `spotNote` in `design/credits.json`: the Website assets page shows it with how it was made, and offers the script and a prompt for visitors.
- Logo size: `composition.logo` in `DESIGN.md`: `standard` (48 px, as tall as the buttons), `large` (56 px on phones, 72 px from tablet width) or `masthead` (on its own row, as wide as the content column). Never shorter than the buttons beside it or in the phone bar. A hero that fills the first screen subtracts `var(--header-height)`, which follows the size.
- Sections follow the page's argument, not a fixed order. The hero comes first and has the only `<h1>`. Each section takes a `variant` (layout) and a `phone` setting (`stack`, `swipe`, `collapse`, `hide`; `auto` uses `PHONE_AUTO` in `src/sections/schema.js`). With `separation: bands`, bands alternate tones automatically.
- On phones, `swipe` suits a set of like items to browse (a wall of services, a gallery); things read in order, or the one thing a visitor must see, go in `stack` or `collapse`. Every swipe strip gets the swipe cue (`src/sections/SwipeCue.astro`: an accent bar with an arrow head; put it right after any new strip) and a note in the QA report. If the home page is longer than the phone budget, fold or hide a section or ask the owner.
- In a set of cards where some carry photos, most do; a type-only card is a deliberate accent, not where the photos ran out. Each photo is chosen for what its card says.
- A design runs through every page: when the look, the image style or a phone rule changes, carry it to the inner pages too. The QA report lists content pages with no pictures.
- One design language: the home page may be louder (a taller hero, more panels), but every page shares the title treatment, the image treatment, the way type meets a picture, and the card and section styles. Pages may vary within the route's family: a hero picks a layout from `composition.heroes.page` with `variant` (without one it gets the first), and the content check holds every page to the family (a hero with no picture may be a statement). Flow runs the whole length of a page: every content page ends on the route's closing section (`composition.closing`), as the home page does, and no page runs longer without a picture than the home page does. A photo goes with the title or with text beside it, never in a bare band under it. Pages the framework generates (contact, privacy, thanks, 404, website assets) set their title with `src/components/PageTitle.astro`. Before showing the owner anything, look at `qa-output/site-sheet-1280.png` and `site-sheet-360.png`: the first screen of every page side by side.
- Text over a picture sits on a scrim or a part of the picture darkened for it; the QA gate measures it against the picture.
- Style guide: once the route is built on the home page, and before the other pages, write `STYLE-GUIDE.md` (brand, logo, colour, type, photography, layout and page flow, components, voice, beyond the website, do and don't; keep every heading) from `DESIGN.md`, `PRODUCT.md` and the owner's decisions, then `node scripts/style-guide.mjs`: it adds the site's real colours with contrast, type scale, components, hero layouts, page flow, the first screen of every page and the cited social and print sizes, and writes `design/style-guide/style-guide.pdf`, `style-guide.png` and `stamp.json` (commit all three). Every later page, post or print piece is made from it. When `DESIGN.md`, `STYLE-GUIDE.md` or the logo changes, render it again: the QA gate fails a guide older than any of them.
- A layout this site needs that the section library lacks is built here, in `src/sections/` (site changes survive framework updates). It moves into Framework B only when a second site needs it.
- A nav item with `"cta": true` in `site.config.json` becomes the header button on wider screens and a fixed action bar on phones (a second one, for a site with two front doors, becomes an outlined button beside it) (with a Call button when `site.phone` is set); phones also get a row of page links. On phones the hero leaves out any action the bar already shows. A section set to `collapse` shows each row with a plus in an accent-outlined square (a minus when open).
- Logo (unless the owner keeps their own: put it in `public/logo.svg` and set `site.logo`): `node scripts/logo.mjs brief` and write `design/brand/brief.md` from `design/research.md` (the business, the site's own look, current design, the field's sea of sameness, clichés to avoid, ideas only this business has); draw five to eight concepts in `design/brand/concepts/<id>.svg` (format at the top of `scripts/lib/logo.mjs`: a mark and a lockup, ink and accent only, holes for cut-outs, words as `<fb-text>`, straight or round a seal with `arc`; each names `data-from`, `data-trend` and `data-look`; `node scripts/logo.mjs measure "<words>"` gives widths); `node scripts/logo.mjs check`, then `sheet`, look at every sheet and send `design/brand/concepts.pdf`; then `pick <id>` (every version, favicons, app and maskable icons, share image, manifest, print PDFs in `design/brand/kit/`, `design/brand/logo.json`, `site.logo`) and render the style guide again. Quick layouts from the display font: `node scripts/logo.mjs templates`, then `sheet` and `pick t<n>`.
- Images in a generated style: `node scripts/generate-image.mjs draft "<subject>" --as <name>`, look at `design/generated/<name>/sheet.png`, then `use <name> <n> --alt "..."`. Needs the Workers AI token (a network secret on the agent's environment, or `WORKERS_AI_TOKEN`) and `CLOUDFLARE_ACCOUNT_ID`; otherwise the ops repo's **site images** workflow runs it with the token kept there. Stock and generated images get the design's treatment automatically; `node scripts/images.mjs treat <file>` applies it to an owner photo. Every generated image is listed on `/credits`; none carries a label on the page.
- The QA gate fails on:
  - a stale tokens.css or design.json, a style guide rendered before the last change to `DESIGN.md`, `STYLE-GUIDE.md` or the logo, or a logo kit with a file missing;
  - a home page longer than the phone budget at 390×844, a first phone screen without the `<h1>`, a missing phone action bar, a link or button the bar cuts in half on the first screen, text left under the bar at the end of the page, or a sideways strip without its swipe cue;
  - anything animating when the visitor asks for reduced motion;
  - a list of three or more cards where some carry photos but half or fewer do;
  - a page title whose face, weight, case or alignment differs from the home page's, a bare photo banner (a photo at least 60% of the window wide and 30% of its height with no text over it or beside it, at 1280 px), or a page that runs more than half a screen longer without a picture than the home page does;
  - a section with less than a tenth of its weight on one side of the middle of the window and nothing a quarter of the way across that half, at 1280 px; a picture cropped by a third or more of its width or height without a focal point on that axis, at 360 and 1280 px; a header logo shorter than the tallest button beside it or in the phone bar;
  - text over an image or gradient below 4.5:1 (3:1 for large text) against the lightest part of the picture behind it (the darkest, for dark text), at 360 and 1280 px;
  - content that doesn't match the schema;
  - reviews, ratings, customer counts or percentages without a source in `PRODUCT.md` (truth gate);
  - generic AI words (copy lint; the owner's own phrases listed under "## Owner's wording" in `PRODUCT.md` are skipped);
  - Impeccable findings in the source or on any rendered page, including any font, colour, radius or font size outside `DESIGN.md`. For a deliberate exception, run `npx impeccable ignores add-value <rule> <value> --reason "..."`; it is recorded in `.impeccable/config.json` for review.

## Rules
- Work on a branch and open a pull request. `main` deploys production immediately.
- Never commit secrets. Secrets are Worker secrets; names are listed in `SECRETS.md`.
- Drips (launch sites with Resend only): add a `drips` block to `site.config.json` (forms, then emails with `after`, `subject`, `text`) and the Workflow binding to `wrangler.jsonc`: `"workflows": [{ "name": "<id>-drips", "binding": "DRIPS", "class_name": "DripWorkflow" }]`. The content check fails without the binding. Write each email from what the owner supplied; never invent offers or proof.
- Never delete or rewrite rows in `leads` or `subscribers` without the owner's explicit approval.
- Never buy a domain, upgrade a plan or create a paid resource without the owner's explicit approval.
- Every form is a sign-up form unless its `consent` is "none" (a plain message form that says it won't add anyone to a list; it shows no opt-in and never subscribes). Keep the opt-in line under the submit button (`optIn.mode` "auto"), or the consent box before it ("checkbox": only a ticked box subscribes; a form's `consent` is "required" or "optional").
- `/go` redirects to `go.to` (default `/`) keeping the query string: point printed QR codes and campaign links at `/go?src=<where>`, and never remove it.
- No invented testimonials, logos, statistics or faces. Use only what the owner supplied.
- Keep internal links extensionless (`/contact`, not `/contact.html`).
- Mark anything not yet proven by a test as "untested".
